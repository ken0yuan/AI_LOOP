# API 适配前置准备

本步按“刷新数据库 → 补全本轮条目 → 生成本次适配任务”的顺序执行。任务名单来自本次问题描述，与文档刷新发现的新增名单分别处理。

## 输入与数据库

所有命令从AI_LOOP根目录执行，相对路径以该目录为基准。

| 输入 | 用途 |
|---|---|
| `data/run_data/<run-id>/basic_information.json` | 读取本次`venv`和`problem-description`，沿用Step 0准备的环境 |
| `data/api-support.sqlite3` | 读取和更新`API支持数据`表，以`API名称`为主键 |
| 官方main文档索引 | 获取全部文档API名称；按需复用对应API文档 |

数据库中每个API保留一行，字段顺序如下：

| 序号 | 字段 | 保存内容 | 作用 |
|---|---|---|---|
| 1 | API名称 | 该行对应的API名称，作为唯一主键 | 按名称定位条目；别名也独立保留一行 |
| 2 | 是否支持 | `支持`、`不支持`、`未提供`、`API删除，待下线`、`文档删除，待下线` | 记录支持结论，并区分wheel中不存在与文档中缺失 |
| 3 | API等级 | 沿用既有`L0`、`L1`、`L2`分级；历史条目可能为`删除`或空值 | 保留API等级信息，与适配方向、三级职责分类分别记录 |
| 4 | API适配分类 | `框架类API`、`算子类API`、`专项适配API`；新增待补全时留空 | 标记API的适配方向，供后续选择处理方式和测试规范 |
| 5 | 是否对外 | `是`或`否`，记录是否属于对外API | 限定公开API的刷新范围，以及重复组中可选的正名范围 |
| 6 | 分类 | 一级职责分类，如`Core`、`基础计算`、`工具`、`分布式`、`图模式` | 确定API的主要职责范围，作为模块和场景分类的上级 |
| 7 | 细分模块 | 所选一级分类下的模块名称 | 在一级职责范围内定位API所属模块 |
| 8 | 细分场景 | 所选模块下的具体场景名称 | 描述API的具体职责，与前两列共同形成完整分类路径 |
| 9 | 适配策略 | `补充testcase`、`已支持`、`依赖CANN算子实现`及其他专项或暂不适配策略 | 决定后续处理方式，例如`补充testcase`进入补充用例流程 |
| 10 | 本地是否适配 | `是`或`否`，记录是否纳入本地适配任务 | 作为任务开关：`是`生成适配任务，`否`跳过该API |
| 11 | 分类待审核 | `是`或`否`，记录分类是否仍需人类审核 | 标识分类审核进度，人类审核通过后由`是`更新为`否` |
| 12 | api首次出现版本 | 首次登记该API的PyTorch主次版本，如`2.14`、`2.15` | 记录版本来源，后续刷新或补全其他信息时保留已有值 |
| 13 | API真正名字 | 别名指向的正名，填写目标行的`API名称`；正名或独立API留空 | 非空时转到正名行读取业务信息，为空时处理当前行；多个别名按正名合并为一个任务 |

只有wheel中确认不存在、标记为`API删除，待下线`的API，才因接口不可用而从补全名单和`task-branches`中排除。`文档删除，待下线`只记录文档缺失，wheel中仍存在时继续按适配策略和本地任务开关处理，不据此判为不支持。

## 第一步：刷新数据库

```bash
python3 -B scripts/refresh_api_support_db.py \
  --basic-information data/run_data/<run-id>/basic_information.json \
  --database data/api-support.sqlite3 \
  --new-apis data/run_data/<run-id>/api-refresh/new-apis.json
```

刷新按以下顺序处理：

1. **获取全量文档API。** 从官方`https://docs.pytorch.org/docs/main/objects.inv`读取全部登记名称和声明目标，保留各公开名称。
2. **与全库主键匹配。** 同名内部条目将`是否对外`改为`是`，沿用原行及原有业务字段，参与后续存在性核验和正名对齐；未登记名称准备新增。其余内部条目保持原样，不参与后续核验和别名比较。已有对外条目的`Tensor`与`torch.Tensor`简写继续兼容匹配。
3. **核验全部文档API是否存在于wheel。** 使用本次`venv`的解释器检查全部名称，包括已在数据库中的名称。确认不存在的条目填`API删除，待下线`，新增名称也保留一行。存在的条目保留已有支持结论；原为下线状态的恢复为`未提供`。
4. **检查文档中消失的对外API。** wheel中仍存在则填`文档删除，待下线`，wheel中也不存在则填`API删除，待下线`。其他内部条目不处理。
5. **比较对象身份，更新正名指向。** 将新增API（含内部转对外）与wheel中存在的存量对外API一起解析。在同一Python进程中保留对象引用，以`id()`建立身份索引，用`is`确认同组对象。每组取完整名称最短的公开API为正名，等长按字典序选择。正名的`API真正名字`留空，其他名称直接填写正名所在行的`API名称`。出现更短正名时，原正名及所有公开旧别名同步直接指向新正名，并沿用该对象已有的业务信息。正名业务字段齐全的条目（包括内部转对外）处理到此结束；有缺项的才进入第二步。
6. **保存并交接。** 同一事务保存新增行、对外标记、支持状态和正名指向。将本轮新入库、内部转对外或恢复上线后仍有业务字段缺项的有效正名写入`api-refresh/new-apis.json`，按正名去重；字段齐全的条目，以及wheel中不存在的名称及其正名不进入补全名单。

对象身份比较只判断同一Python对象，功能相同但`is`为假的入口分别保留。仅有声明的实例字段、普通数值和布尔等字段保留扫描记录，不参与对象判重。导入或依赖异常属于核验失败，不作为API不存在的依据。

新增行的`是否对外`填`是`、`分类待审核`填`是`，首次出现版本取本次main索引对应的主次版本；三级分类、`API适配分类`及其他业务字段交给第二步填写，入库时不预填`API适配分类`。已有行的首次出现版本保持原值。

入口成功返回`DATABASE_REFRESHED`。读取本轮`new-apis.json`：非空进入第二步，为空跳过第二步，直接处理第三步的任务需求。索引及wheel核验结果保存在本次运行目录的`log/api-refresh/`中。

## 第二步：补全本轮API条目

只处理第一步交付的、有业务字段缺项的有效正名。只填写缺失字段，已有值保持原样；字段齐全的条目不进入本步。

### 1. 读取条目并复用文档

按`new-apis.json`中的名称读取数据库；先过滤wheel中不存在的条目，再通过`API真正名字`定位正名并去重。需要补全时使用本次版本的官方API文档。

同一运行中，已取得的文档直接复用，缺失页面按需获取一次。索引中的名称清单不等于API正文；三级分类、适配分类和后续用例生成共用本轮取得的材料，不各自重新抓取一份。

### 2. 完成分类与补全其他字段

三级分类有缺项时，按[API三级分类规则](../references/api-classification/rules.md)及对应分类定义，依照`分类`、`细分模块`、`细分场景`的层级补齐，保留已有层级和值。缺少官方正文时，按名称和所属对象给出缺失项的候选分类，在本轮说明中标明依据并保持待审核。

`API适配分类`缺失时，结合`分类`和`细分模块`填写初分类别：

| 分类 | 细分模块 | API适配分类 |
|---|---|---|
| 基础计算 | 基础计算 | 算子类API |
| 基础计算 | 其他模块 | 框架类API |
| 其他分类 | 任意模块 | 框架类API |

分类相关缺项在本步骤一并补齐，不额外提取文档或独立判断。该结果作为后续生成用例的初始类别，生成用例时继续核验是否符合API职责。

缺失项按下表补齐，已有业务值不重填：

| 字段 | 补全方式 |
|---|---|
| API名称 | 沿用正名所在行的主键 |
| 是否支持 | 空值填`未提供`，已有支持结论保留 |
| API等级 | 空值填`L2`，已有等级保留 |
| API适配分类 | 缺失时按上述两级分类映射填写 |
| 是否对外 | `是` |
| 分类、细分模块、细分场景 | 只补齐缺失的分类层级 |
| 适配策略 | 空值填`补充testcase`，已有策略保留 |
| 本地是否适配 | 空值填`是`，已有开关保留 |
| 分类待审核 | 本轮补入分类的条目填`是`；其他条目保留原标记 |
| api首次出现版本、API真正名字 | 沿用第一步维护的值 |

若现有职责定义无法容纳该API，在本轮说明中记录候选标签、父级和原因，分类保留待审核。共享定义的修订在审核后处理。

### 3. 保存并写入结果

数据库保存分类结果。本轮文档缓存、简短分类原因及候选定义放在本次`run-id`目录下，不建立供下次运行复用的长期分类说明库。

- `api-classification/classification-evidence.jsonl`：按正名保存本轮三层分类的简短原因，以及需要审核的候选定义。
- `api-entries.jsonl`：每行提交一个待更新正名的前十一列业务字段，使用数据库中文列名；已有字段照带原值，仅缺失字段填写补全结果。首次出现版本和正名指向由刷新步骤维护，不放入本次业务写入数据。

```bash
python3 -B scripts/update_api_support_entries.py \
  --basic-information data/run_data/<run-id>/basic_information.json \
  --database data/api-support.sqlite3 \
  --new-apis data/run_data/<run-id>/api-refresh/new-apis.json \
  --entries data/run_data/<run-id>/api-entries.jsonl
```

只更新本轮需要补全的正名，保留其他条目和另外两列。写入成功后删除临时`api-entries.jsonl`，返回`API_ENTRIES_READY`。整批均可复用时直接进入第三步。

## 第三步：生成本次适配任务

任务来源是`basic_information.json.problem-description`，不是文档刷新发现的新增名单。没有新增API，也要处理本次需求中的已有API。

```bash
python3 -B scripts/prepare_adapt_information.py \
  --basic-information data/run_data/<run-id>/basic_information.json \
  --database data/api-support.sqlite3
```

逐API按以下顺序选择：

1. **匹配名称。** 从问题描述提取明确的API名称，先精确匹配数据库，再兼容已有的Tensor简写。短名称须在需求中明确标明；未登记名称返回缺项，不取父模块代替。
2. **过滤原名称。** `是否对外`为`否`或`是否支持`为`API删除，待下线`时跳过，记录原因；即使它的别名指向可用，也不借跳转重新下发该名称。
3. **定位并核验正名。** `API真正名字`非空时读取对应正名行，再检查正名是否对外、是否标记为`API删除，待下线`；wheel中不存在的正名同样跳过。正名缺失或指向异常时先修正关系。
4. **检查任务开关。** 正名的`本地是否适配`为`是`才进入任务名单，为`否`则跳过；空值先补齐。支持状态为`不支持`或`未提供`的API可以进入适配任务。
5. **按正名去重并输出。** 保留正名在本次需求中首次出现的顺序，只生成`adapt-<正名的数据库API名称>`。输入别名与正名的对应关系、跳过项及原因记录在本轮结果中。

输出示例：

```json
{
  "task-branches": [
    "adapt-Tensor.add",
    "adapt-torch.nn.functional.relu"
  ]
}
```

至少有一个有效任务时，更新本次`adapt-information.json`，返回`ADAPT_INFORMATION_READY`。无有效任务时返回`NO_ADAPTATION_REQUIRED`并停止；首次运行不创建任务文件，已有文件则将`task-branches`更新为空数组，清除旧开发计划，保留其他任务资料和必要的Git恢复记录。

每次重跑都按当前数据库重建名单，替换旧`task-branches`，同步清除失效的`adapt-plan`等派发结果。混合任务只保留可下发项，全部被过滤时不进入后续步骤；旧名单或Git快照不能把wheel中已不存在的API重新加入待下发名单。

## 输出与完成条件

| 位置 | 内容 |
|---|---|
| `data/api-support.sqlite3` | 更新后的API条目、对外标记、wheel存在性、文档状态和正名指向 |
| 本次`api-refresh/new-apis.json` | 本轮需补全的有效正名 |
| 本次`api-classification/` | 本轮使用的文档缓存、分类原因和候选定义 |
| 本次`adapt-information.json` | 本次需求中可下发的、按正名去重后的任务数组 |

完成本步时，公开名称不重复入库，其他内部条目保持原样；别名直接指向正名；本轮条目已补全或沿用有效结果；最终任务名单中没有wheel中已不存在的API。代码开发和测试由后续适配步骤负责。
