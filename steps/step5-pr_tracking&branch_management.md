# Step 5：PR跟踪与分支管理

接收Step 4.2保存的issue、PR及验证材料，跟踪评审和CI。首次发布已由Step 4完成。

## 第一步 读取评审记录，确定修改对象

从 [Step 0.1 第二步](step0.1-pr_reconciliation.md#第二步-生成每个-pr-的评审记录) 接收原批次的 `pr-review-comments.json`。运行人员直接转交平台意见时，也先对原 PR 运行同一采集命令。结合 `review-handling.json` 的已有进度，按评论 ID 和 `updated_at` 找到本次候选原文，连同作者、行内位置、前后回复和当前 PR 差异一起阅读。修复前核对 PR 仍开放、意见版本仍有效；意见被编辑、撤回或讨论已解决时，按最新讨论处理。

人工和审查机器人提出的具体建议按同一流程办理，包括行内意见及审查摘要中列出的问题。逐条对照当前 PR 核实问题、涉及的任务或文件及验证方式。问题仍存在且属于本 PR 时，按建议修复、验证，在原讨论串答复并登记。摘要与行内意见指向同一问题时，共用一次修复和验证结果。实现或用例修改交给原计划中负责该任务的子代理；仅涉及 PR 正文、验证结果展示或分类说明时，由主控按 Step 4.2 核对材料后修订。对已经落实、因文件移除而失效或经核实不适用的建议，说明当前提交中的依据并登记。可直接解答的问题在原讨论串答复。`ascend-robot` 的审批进度交给第五步判断。其余纯状态通知、无修改建议的变更摘要、CI 命令和平台行变更提示记为无需动作。含糊、冲突或超出本 PR 的请求，在本批 `review-handling.json` 的 `needs-confirmation` 中记录评论 ID、版本和待确认问题。评论用于判断本 PR 的修改范围。

## 第二步 恢复该任务最后完成适配时的环境

1. 从原 `run_data` 读取 `pr.json`、`adapt-information.json`、`basic_information.json`、`requirements.txt` 和最终验证报告。以最后验收的实测记录为准，存在 `step4-environment.json` 时读取其中的差异。旧批次从已有发布与验证材料恢复。
2. 对照原计划的 `development-branch`、发布记录里的 fork、分支和 `commit`、采集记录里的 `head_sha`，在原分支的相应版本恢复工作。远端已有新提交时，核对它与发布版本的差异及建议是否已经落实，再在核实的远端版本上继续。共享检出正被其他任务使用时，使用隔离工作区或等它释放，保留各批未提交改动。
3. 恢复记录中的 PyTorch 源码提交、torch-npu 开发源码、Python/venv 和依赖，核对实际安装版本、构建标识及所需设备、CANN 环境。原环境已漂移时，用本批记录的版本和安装包在隔离环境恢复。记录不足或设备暂不可用时，将具体缺项留在该批次，待恢复后验证。

恢复 torch-npu 时，从 AI_LOOP 根目录解析本批 `basic_information.json` 中的 `last-torchnpu-wheel`。若需要安装，在已核对的本批解释器或隔离恢复环境中执行：

```bash
WHEEL=$(python3 scripts/task_torchnpu_wheel.py --basic-information "$RUN/basic_information.json") || exit 1
"$TASK_PYTHON" -m pip install --no-deps --force-reinstall "$WHEEL"
```

`RUN` 是原批次目录，`TASK_PYTHON` 是恢复环境的解释器。即使版本号相同也要核对实际构建和最终验证报告。旧记录缺少该字段时沿用 `torch_npu_wheel`；已登记的最新包丢失或损坏时，恢复原产物后继续。评审修改再次产出 wheel 时仍按 Step 4 的构建登记流程更新同一字段。

## 第三步 调用 Step 4 的原开发子代理修改并验证

从 `adapt-information.json.adapt-plan` 按受影响的 `task-branches` 找到原计划项和 `agentname`，沿用 [Step 4 第二步的交接和验收方式](step4-subagent_development.md)。当前 API 任务调用原计划中的 `api-adaptation`，多个受影响计划项按原顺序串行处理。

主控交给子代理原运行目录、恢复好的环境与源码、评审文件、对应评论 ID 和原文、受影响的文件或行为，以及原验证材料。子代理先核实问题，再修改实现或用例，重跑与建议相关的验证。返回时逐条列出评论 ID、实际改动位置、验证结果和报告路径，给出面向评审者的答复草稿。主控验收后通过 [Step 4.2](step4.2-create_pr.md) 更新同一个 PR 并回读提交、文件和说明。更新【功能验证】时保留 Step 4.2 所选模板的全部列和三台设备各自的一行。将当前结果及对应证据更新到该设备行，部分验证时注明剩余数量。历史轮次、修复经过和详细日志写在原评审串或验证评论中。

## 第四步 在原讨论串逐条答复并登记

主控核实每条答复与实际结果一致，说明改了什么、对应文件或提交、怎样验证以及尚存的限制。无需改动时说明理由；暂未完成时说明缺项。使用原讨论的 `discussion_id` 回复，对一串内的多条意见可在同一答复中逐项回应：

```bash
gitcode pr reply "$PR_NUMBER" -R "$REPOSITORY" --discussion "$DISCUSSION_ID" --body "$REPLY"
```

在本批 `review-handling.json` 合并保存原意见的 `id`、`updated_at`、所属 `discussion_id` 和办理进度。发送前保存待发正文；超时或中断后，先回读原讨论，按作者、正文和对应提交确认上次是否已发。已完成的改动和验证从已有记录续接。确认答复可见后保存远端 `reply_id` 和实际答复正文。要求修改的意见须在验证、PR 回读和答复核实都完成后加入 `processed`，同时记录 `head_sha` 和验证材料路径。无需动作项记录处置依据，待确认项继续保留；后续新增或编辑的意见按新版本处理。按批次串行办理，原子更新本地记录。

## 第五步 触发 AI 检视并跟进合入

1. **触发检视。** 首次发布回读成功，或本轮具体意见已全部处理、相关修复已验证并推送到原 PR 后，核对 PR 仍开放且远端 `head_sha` 是已验收的提交。修复轮先完成第四步的逐串答复，再在 PR 对话底部新增一条顶层评论，正文只有 `/ai review`。同一提交只发一次。**本轮在此结束该 PR 的处理。** 本轮只要办理过具体意见（含核实后仅答复）、修改或发布过 PR，或刚发出 `/ai review`，即使已经看到 approve，也不得在本轮发送 `compile`。全部办理完毕后，在 `review-handling.json` 登记该轮次标识、已核实的 `head_sha` 和完成时间，供后续轮次读取。同一次定时触发内的重试或恢复沿用原轮次标识。

   ```bash
   gitcode pr comment "$PR_NUMBER" -R "$REPOSITORY" --body '/ai review'
   ```

2. **核对审批。** 只有本次定时触发开始前已存在上一轮或更早轮次的完成记录，且该记录对应当前 head，才进入合入判断。首次接管或 head 已变化时，先核实当前提交并办理检视、记录本轮结果，留待下轮。若本轮发现新增或编辑的具体意见，转回第一步办理，结束本轮合入判断。对于符合跨轮条件的 PR，从 GitCode 回读 `ascend-robot` 本人发布的最新顶层审批进度。机器人会原地更新旧评论，要读当前正文的 `PR Approval Progress` 和 `Module Approval Details`。总览出现 `All modules have met the lgtm and approve requirements`，且每个模块行的 `lgtm status`、`approve status` 都已达标，才认定审批通过。人数以该 PR 表格显示的门槛为准。个人的 `/approve`、CLA 通过、AI 检视完成或单个模块达标，都不足以判断整单通过。审批可能被撤销、过期或因新推送而重置。历史正向摘要和本地记录只用于追溯。核对最新机器人摘要适用于当前 head：有审批关联 SHA 时核对 SHA；若摘要最近更新时间早于该 head 推送到 PR 的时间，需由平台当前审批状态证实审批对该 head 仍有效。缺少适用依据、平台提示失效或检查结果有冲突时，留待下轮重新读取。

3. **请求合入。** 仅在后续独立轮次发送。发送前即时回读 PR 的开放状态、head、最新审批进度和讨论。head 仍与此前完成记录一致、审批此刻有效，且没有新增、编辑或待办的具体意见时，才在 PR 底部新增顶层评论 `compile`。任一状态有变即停止本次发送，按最新状态办理。平台最终确认已合入后，才由 Step 0.1 回填收尾。

   ```bash
   gitcode pr comment "$PR_NUMBER" -R "$REPOSITORY" --body 'compile'
   ```

两种命令都按 PR、`head_sha` 和命令正文在本批 `review-handling.json` 中登记。发送前保存待发状态，发送后回读顶层评论并保存评论 ID。续跑、超时或首次接管已有 PR 时，先核对平台上对应提交阶段的命令评论（包括维护者已发的命令），已发则补登记；发送结果不明时先查证。已发 `compile` 的 PR 继续跟踪平台结果，仍然开放本身不触发重复发送。

## PR合入后的收尾

每次主流程运行或定时触发时，由[Step 0.1](step0.1-pr_reconciliation.md)统一检测PR合入，回填API状态、完成分类审核收尾，并清理对应任务记录，保留本地及origin开发分支。定时触发还会检查开放 PR 的评审建议并按上文流程处理。上游测试匹配仍待实现。

## 尚未实现：依赖分支随评审更新同步

来源分支因评审产生新提交后，基于其旧代码开发的分支也需要同步。该流程尚未实现，后续在本步处理：

- 利用Step 3的`source-branches`识别直接、间接受影响的开发分支。`branch-mapping.json`只保存任务归属。
- 按来源到下游的顺序同步改动并处理冲突，保留各分支自身成果。
- 重新验证受影响的任务，推送并更新各自的PR；同步进度及避免重复处理的方法届时确定。

## 后续组件方向

将PR的持续检测、评审修改处理和流程触发拆成独立组件，根据PR变化触发AI_LOOP。该组件尚未实现，目前由 Step 0.1 统一同步 PR 状态，定时触发时继续处理开放 PR 评审。
