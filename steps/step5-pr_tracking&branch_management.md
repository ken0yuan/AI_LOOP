# Step 5：PR跟踪与分支管理

Step 5 处理 Step 0.1 交来的 PR 评审意见，并跟踪这个 PR 的检视、审批和合入进度。

## 第一步 读取评审记录，分派意见

从 [Step 0.1 第二步](step0.1-pr_reconciliation.md#第二步-生成每个-pr-的评审记录) 接收原批次的 `pr-review-comments.json`。运行人员直接转交平台意见时，也先对原 PR 运行同一采集命令。结合 `review-handling.json` 的已有进度，按评论 ID 和 `updated_at` 找到本次候选原文，连同作者、行内位置、前后回复和当前 PR 差异一起阅读。修复前核对 PR 仍开放、意见版本仍有效；意见被编辑、撤回或讨论已解决时，按最新讨论处理。

主控按意见涉及的内容分派，人工和机器人的意见用同一套规则。一条评论里有几个独立问题，就拆开分派；行内评论和评审摘要提到同一问题时，合并处理并保留各自的评论 ID。

- **涉及实现、用例、断言或 API 行为**：主控找到对应的原计划项，交给其 `agentname` 指定的子代理判断是否需要修改。
- **只改 PR 正文、分类说明或验证表**：由主控按 Step 4.2 的模板修改。
- **查询已有记录**：例如询问验证报告在哪、某个文件是否还在 PR 中，主控查阅批次记录或当前 PR 差异，按第四步在原串答复。
- **需要确认**：意见含糊、互相冲突或超出本 PR 范围时，把评论 ID、版本和待确认的问题记入 `needs-confirmation`。

`ascend-robot` 的审批进度留到第五步查看。纯状态通知和 CI 命令记为无需处理。

主控直接办理的事项按第四步答复和登记。需要子代理判断的技术意见，进入第二步恢复环境，再按第三步交接。

## 第二步 恢复该任务最后完成适配时的环境

1. 从原 `run_data` 读取 `pr.json`、`adapt-information.json`、`basic_information.json`、`requirements.txt` 和最终验证报告。以最后验收的实测记录为准，存在 `step4-environment.json` 时读取其中的差异。旧批次从已有发布与验证材料恢复。
2. 对照原计划的 `development-branch`、发布记录里的 fork、分支和 `commit`、采集记录里的 `head_sha`，在原分支的相应版本恢复工作。远端已有新提交时，核对它与发布版本的差异及建议是否已经落实，再在核实的远端版本上继续。修改前记下这个已核实的完整 SHA 作为本轮 `EXPECTED_HEAD`，交给 Step 4.2 覆盖推送时核对。共享检出正被其他任务使用时，使用隔离工作区或等它释放，保留各批未提交改动。
3. 恢复记录中的 PyTorch 源码提交、torch-npu 开发源码、Python/venv 和依赖，核对实际安装版本、构建标识及所需设备、CANN 环境。原环境已漂移时，用本批记录的版本和安装包在隔离环境恢复。记录不足或设备暂不可用时，将具体缺项留在该批次，待恢复后验证。

恢复 torch-npu 时，从 AI_LOOP 根目录解析本批 `basic_information.json` 中的 `last-torchnpu-wheel`。若需要安装，在已核对的本批解释器或隔离恢复环境中执行：

```bash
WHEEL=$(python3 scripts/task_torchnpu_wheel.py --basic-information "$RUN/basic_information.json") || exit 1
"$TASK_PYTHON" -m pip install --no-deps --force-reinstall "$WHEEL"
```

`RUN` 是原批次目录，`TASK_PYTHON` 是恢复环境的解释器。即使版本号相同也要核对实际构建和最终验证报告。旧记录缺少该字段时沿用 `torch_npu_wheel`；已登记的最新包丢失或损坏时，恢复原产物后继续。评审修改再次产出 wheel 时仍按 Step 4 的构建登记流程更新同一字段。

## 第三步 由原开发子代理核实技术意见，按需修复和验证

按受影响的 `task-branches` 在 `adapt-information.json` 的 `adapt-plan` 中找到原计划项。调用该项 `agentname` 指定的子代理，按 [Step 4 第二步](step4-subagent_development.md) 的方式交接和验收。涉及多个计划项时，按原计划顺序逐项处理。

主控提供原批次运行目录、已恢复的环境与源码、评论 ID 和原文、涉及的文件或行为，以及已有验证报告。

子代理对照当前提交逐项判断。评审质疑 API 行为时，查目标版本源码或运行最小用例。例如，对 `Fold(4, 3).extra_repr()` 的输出有争议，就在目标版本运行这个调用，核对实际字符串。评审质疑测试时，找出对应输入和断言，说明评审所指出的错误会让哪条断言失败；同时检查断言是否限定了无关细节、覆盖说明是否超出了实际用例。

意见成立的部分由子代理修复并验证；保留原写法的部分给出源码或实测依据。仅删除文件、修改 PR 正文或答复意见时，主控按 Step 4.2 核对保留的文件，复用与当前文件和设备匹配的验证记录。

1. **子代理交回结果。** 每条评论附上 ID、判断依据和答复草稿。有改动时，列出改动位置和验证报告路径。
2. **主控验收。** 对照原意见检查答复和证据。哪一项没有说清，就把那一项退回原子代理补充。
3. **更新原 PR 后答复。** 需要改代码、正文或验证表时，按 [Step 4.2](step4.2-create_pr.md) 更新原 PR，并回读提交、文件和正文。推送代码使用第二步记录的 `EXPECTED_HEAD`。回读通过后进入第四步；只需答复的意见可直接进入第四步。

## 第四步 在原讨论串答复、标记解决并登记

1. **回复原串。** 按[PR 正文和评论怎么写](../references/pr-writing.md)简短答复每个问题；仍待办理的写清缺项。发送前在本批 `review-handling.json` 保存原意见的 `id`、`updated_at`、`discussion_id` 和答复草稿。同一串的多个问题可合并答复。

   先回读原串。已有对应当前意见和提交的有效答复时，直接复用；否则发送草稿：

   ```bash
   gitcode pr reply "$PR_NUMBER" -R "$REPOSITORY" --discussion "$DISCUSSION_ID" --body "$REPLY"
   ```

   确认答复可见后，保存远端 `reply_id` 和实际正文。发送超时或中断时，先按作者、正文和对应提交核对是否已发，再决定是否重试。

2. **解决整串。** 对人工或机器人提出的行内讨论（`comment_type=diff_comment`），按 `discussion_id` 回读全部意见和回复。整串意见均已答复，所需修改和验证均已完成，才将仍为「待解决」的讨论标记为「已解决」。还有待修、待测、待确认或新意见时，保留「待解决」。

   ```bash
   printf '%s\n' '{"resolved":true}' | gitcode api "repos/$REPOSITORY/pulls/$PR_NUMBER/comments/$DISCUSSION_ID" --method PUT --input -
   ```

3. **登记结果。** 重新采集原 PR 的评论。行内讨论只有在同一 `discussion_id` 回读到 `resolved=true` 后，才将已办理的意见版本记入 `processed`。标记失败或超时也先回读；仍未解决就保留待办。普通评论按实际处置登记：已答复的核对远端回复，无需动作的记明依据，待确认的留在 `needs-confirmation`。凡涉及修改，登记完成前还须核实验证结果、原 PR 的改动和答复，记录 `head_sha` 与验证材料路径。

**跨轮待办。** GPU 复测仍在运行或受阻时，记录对应提交、待验证项及请求 ID 或受阻原因。下轮从已有进度续办，即使 `candidate_count=0` 也继续追踪，直到报告与当前文件匹配并回填原 PR。新增或编辑的意见按新版本办理。

**记录维护。** 按批次串行办理，将进度原子合并写入本批 `review-handling.json`。汇总待办时注明最近一次采集时间。

## 第五步 触发 AI 检视并跟进合入

1. **判断是否发送 `/ai review`。** 回读原 PR 的顶层命令、机器人最新结论和相关讨论，按以下情况处理：

   - **首检。** PR 首次发布并回读成功后，确认整个 PR 从未发起过 AI 检视，才发送一次。已有命令或检视结果的 PR 按已有检视跟踪。
   - **等待或结束。** 命令已发、结论未出时，等待该次检视结果。上一轮没有新增问题，或 AI 检视结论为「未发现问题」，该轮检视结束，不再发送。换了提交、重新跑定时任务或补标旧讨论，都不能单独触发复审。
   - **复审。** 只有上一轮确实提出了新问题，且该轮意见已全部解决，才再发一次。逐条核对所需修复已验证并推送、答复已可见、行内讨论已标为「已解决」。发送前确认 PR 仍开放、当前提交已验收。按这批意见和办理时间核对顶层命令，维护者或流程已经为这批处理结果发过的，跟踪该次复审。归属不清时先查证。

   **本轮在此结束该 PR 的处理。** 本轮只要办理过具体意见（含核实后仅答复）、修改或发布过 PR，或刚发出 `/ai review`，即使已经看到 approve，也不得在本轮发送 `compile`。全部办理完毕后，在 `review-handling.json` 登记该轮次标识、已核实的 `head_sha` 和完成时间，供后续轮次读取。同一次定时触发内的重试或恢复沿用原轮次标识。

   ```bash
   gitcode pr comment "$PR_NUMBER" -R "$REPOSITORY" --body '/ai review'
   ```

2. **核对审批。** 按顺序检查三项：

   - **提交和意见。** 本次定时触发开始前，应已有上一轮对当前 `head_sha` 的完成记录。首次接管或提交已变更时，先核实并记录本轮结果，按上文判断是否需要检视，留到下轮再判断合入。有新增或编辑的具体意见时，回到第一步处理。
   - **模块票数。** 回读 `ascend-robot` 最新的顶层审批评论，读取当前正文（机器人会原地更新）。`PR Approval Progress` 应显示 `All modules have met the lgtm and approve requirements`，且 `Module Approval Details` 中每个模块的 `lgtm status` 和 `approve status` 都达到该表的门槛。
   - **审批仍然有效。** 平台提供审批关联 SHA 时，核对它与当前提交一致。若审批评论最后更新时间早于当前提交的推送时间，再查平台对当前提交的审批状态。审批已失效、依据不足或结果冲突时，留到下轮核对。

3. **请求合入。** 仅在后续独立轮次发送。发送前即时回读 PR 的开放状态、head、最新审批进度和讨论。head 仍与此前完成记录一致、审批此刻有效，且没有新增、编辑或待办的具体意见时，才在 PR 底部新增顶层评论 `compile`。任一状态有变即停止本次发送，按最新状态办理。平台最终确认已合入后，才由 Step 0.1 回填收尾。

   ```bash
   gitcode pr comment "$PR_NUMBER" -R "$REPOSITORY" --body 'compile'
   ```

**命令登记。** 在本批 `review-handling.json` 按 PR、`head_sha` 和命令正文记录每次发送。发送前记为待发，发送后回读顶层评论并保存评论 ID。复审还需关联本次已解决的意见 ID。首次接管、续跑或发送超时时，先回读平台，包括维护者发出的命令。已有对应评论就补登记；确认未发出才发送，结果不明时继续核对。

**已发送的 `compile` 按平台结果处理：**

- **仍在排队、执行中或没有明确结果**：继续跟踪这次命令。发送评论时的网络超时，不能作为编译任务已失败的依据。
- **平台确认本次任务超时，或因可重试的执行故障失败**：进入 Step 5 的定时轮次按第 2、3 项重新核对当前提交、审批和待办。条件仍满足，且同一提交尚未重试时，在原 PR 再发一次 `compile`。重发前登记原命令 ID、失败回执和待发的重试，发出后补记新评论 ID。平台上已有的重发也计入这一次。
- **一次重试仍失败，或失败原因需要修改代码**：登记失败原因和待办，交给对应任务处理。这个提交停止自动重发。已成功的继续跟踪合入结果。

## PR合入后的收尾

每次主流程运行或定时触发时，由[Step 0.1](step0.1-pr_reconciliation.md)统一检测PR合入，回填API状态、完成分类审核收尾，并清理对应任务记录，保留本地及origin开发分支。定时触发还会检查开放 PR 的评审建议并按上文流程处理。上游测试匹配仍待实现。

## 尚未实现：依赖分支随评审更新同步

来源分支因评审产生新提交后，基于其旧代码开发的分支也需要同步。该流程尚未实现，后续在本步处理：

- 利用Step 3的`source-branches`识别直接、间接受影响的开发分支。`branch-mapping.json`只保存任务归属。
- 按来源到下游的顺序同步改动并处理冲突，保留各分支自身成果。
- 重新验证受影响的任务，推送并更新各自的PR；同步进度及避免重复处理的方法届时确定。

## 后续组件方向

将PR的持续检测、评审修改处理和流程触发拆成独立组件，根据PR变化触发AI_LOOP。该组件尚未实现，目前由 Step 0.1 统一同步 PR 状态，定时触发时继续处理开放 PR 评审。
