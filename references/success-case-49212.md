**问题与分析 → 创建或复用 issue → 明确本批 API 和开发分支 → 生成 / 修改代码 → 实际测试与修复 → 汇总发布材料 → commit、push、PR → 评审后继续修复与回归。**

## 从代码学到的执行细节

1. **生成围绕 API 真实契约。** 逐 API 有签名、覆盖维度和实际 `unittest` 断言。抽读的 zero_grad 用例区分置 None、原位清零、引用保持及默认行为；step 用例检查参数更新、状态及数值结果。不能仅生成能导入的空文件或为了异常覆盖虚构报错。
2. **同一批测试支持不同设备执行。** 代码探测可用 NPU，否则选择 CUDA / CPU，并按情况导入 torch_npu；浮点结果可以与 CPU Golden 对照。运行前确认最终实际使用的设备，不能在 NPU 不可用而回退 CPU 时仍记录“NPU 通过”。不将其中具体阈值或后端特例无条件套用其他 API。
3. **测试开关影响实际执行。** 83 份文件均读取 `RUN_SUPPLEMENT_API_TESTS`。运行本类补充测试必须按代码要求显式启用，统计执行、通过、失败、跳过；进程成功退出但整批跳过不构成验证。
4. **NPU 与 GPU 记录是不同设备的实际产物。** 根据本批约定分别取得所需记录，不能从一个设备推断另一个设备成功，也不能重复使用案例截图。纯 CPU 参照不能自动替代要求的 GPU 验证。
5. **失败修复属于闭环。** 最终提交信息还记录了格式检查修正。失败后修改代码必须验证受影响部分，发布只使用与最终改动相符的记录，不能继续引用旧版结果。

单文件测试可按已有环境和脚本入口组织调用，例如 `RUN_SUPPLEMENT_API_TESTS=1 "$PYTHON" "$TEST_FILE"`。这只是依据代码约束给出的调用形式，不是从历史截图恢复出的原始命令，也不替代本批设备检查、完整范围执行和日志收集。
