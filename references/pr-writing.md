# PR 正文和评论怎么写

## 1. 开发做法怎么写（正文【修改方案】）

逐个看 PR 最终保留的改动。实现文件写清哪个函数实现了这次要适配的功能，或哪个已有功能改了、原来怎样、现在怎样。测试文件写清测了哪些场景。文件里如果只是整理导入、调整排版或抽取辅助函数，且已有行为照旧，就跳过整个文件。

按下面的 Markdown 格式填写。每个入选文件以仓库相对路径独占一行，文件之间空一行。按实际改动保留对应条目，纯测试 PR 直接从测试文件开始。

```markdown
**`实现文件路径`**

- `重要函数名` 或功能名：写清它实现了什么。
- 已有行为变化：写清触发条件、原有行为和当前行为。

**`测试文件路径`**

- 写明一个测试场景的条件和预期结果。
```

发布或更新前逐项核对：每个重要函数或功能各占一项，每项已有行为变化单列。测试文件每行一个场景，去除函数与文件名后的说明文字通常 50 字左右。评审修复改变交付范围或行为时，直接更新对应条目，移除已撤下的内容。

## 2. 测试验证怎么写（正文【功能验证】）

固定版本和 nightly 测试均用 unittest 驱动。功能验证表每种硬件型号一行，补测后更新原行。五列按以下口径填写：

- **执行端及设备**填 NPU 或 GPU 和实际型号。
- **实测包版本**填 PyTorch 完整版本，NPU 另填 torch-npu 完整版本。
- **JUnit 统计**照录报告的 tests、failures、errors、skipped 计数。报告只覆盖本次补测时注明范围。没有生成报告就填“未生成”。
- **测试退出码**填测试进程的实际值。已运行但无记录填“未记录”，整组尚未运行填“—”。
- **执行状态**用一句话写当前提交在该设备上的最终结果，分母取本 PR 在该设备上需要验证的全部用例数。全部通过写“完整，42/42 通过”。有失败、
错误或跳过时写明各自数量。

在功能验证表下，每个设备各占一行，写成「执行端及设备：本轮结果的说明」。设备名与表格对应，说明不超过 100 字。每次更新pr或测试结果或代码时，删除原先的设备测试说明，重新撰写，不要保留过时消息。

有 CPU 回退时按设备运行记录区分，例如“10/12 在 NPU 通过，2 条回退 CPU 后通过”。有用例未执行写“7/12 通过，5 条未执行”，整组未执行写“待验证”。只验证纯 Python 契约时写“48/48 通过（纯 Python 契约）”。

## 3. 评审意见怎么回（原讨论串）

默认一两句，直接答评审人提出的问题。采纳的，点明改了什么。只有原意见问到验证或需要实测才能回答时，才补相关结果。保留原写法的，给出对应版本的源码或实测依据。还没完成的，说清剩哪项。一个讨论串有几个独立问题，就逐项短答。

例：评审指出 `mat2` 形状写反时，回复“已改为 `(k, n)`。”

各设备的最终结果更新到 PR 正文对应行。评审人索要报告时，在原串贴链接。
