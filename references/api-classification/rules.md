# API 三级分类规则

本规则用于补齐正名行的`分类`、`细分模块`、`细分场景`缺项，已有层级和值保留，别名行不补业务字段。`API适配分类`是另一列，其初分与字段写入按[Step 2.1](../../steps/step2.1-api_prepare.md)执行，不在这里重复定义。

先查本次版本的官方API文档，弄清楚它操作什么对象、做什么事情。类成员还要看所属类的用途。没有文档时，可以根据名称和所属对象推断，但要在简短原因中说明“按名称推断”。

已有分类直接复用，不要求先找到以往运行的说明。存在缺失层级时，按下面三步补齐，并保留已有父级；本轮需要判断的层级各写一句简短原因。

## 第一次划分：选分类

按API的主要作用，从下表选一项。命名空间用于找文档，不能单凭`torch.xxx`前缀决定分类。

| 分类 | 什么时候选 | 下一步读哪个文件 |
|---|---|---|
| Core | 管理设备、存储、自动求导、混合精度、算子注册或模型打包导出等框架运行能力 | [core.md](core.md) |
| 基础计算 | 创建或计算张量，或进行神经网络、优化、概率、稀疏、量化等数值计算 | [compute.md](compute.md) |
| 工具 | 提供数据加载、开发测试、测量诊断、可视化或训练内存优化等辅助能力 | [tools.md](tools.md) |
| 分布式 | 完成跨进程通信、并行训练、分布式状态管理或相关运行保障 | [distributed.md](distributed.md) |
| 图模式 | 捕获、表示、变换、编译或重放程序图，以改变模型执行方式 | [graph.md](graph.md) |

先按主要目的区分：模型打包导出看Core，执行期图编译看图模式；量化流程即使用到FX图，也先看基础计算的量化定义。具体边界以对应定义文件为准。

## 第二次划分：在这个分类里选细分模块

1. 打开上表指定的文件，先读开头的“细分模块定义”表。
2. 对照每个模块的“职责定义”和“相邻模块的边界”，找出哪个模块负责这项API的主要工作。
3. 只在第一次选定的分类内选择。若多个模块都像，比较它们的边界，选职责最直接的一项，不按名字相似程度选择。
4. 选定模块，填写`细分模块`，用一句话说明API的作用为什么符合该模块定义，然后再选场景。

例如，神经网络激活函数先归入“基础计算”这个分类；在该分类的模块表中，应比较“基础计算”“神经网络”等模块的定义，不能因为一级分类叫基础计算，就把二级模块也直接填成基础计算。

同时到`data/run_data/<run-id>/api-classification/classification-evidence.jsonl`查找`level=module`且`parent=[所选分类]`的候选模块，与表内模块一起比较。若一级分类本身还是候选、尚无定义文件，就从这些候选模块中选择。已有候选也要检查职责是否匹配，不能直接照抄。

所有模块都不适用时，先检查第一次分类是否选错。第一次没有选错，才按下文判断是否提出新模块。

## 第三次划分：在这个模块里选细分场景

1. 在同一个定义文件中，找到“所选模块名 + 中的细分场景”这一节，例如“基础计算中的细分场景”。
2. 只比较这一节中的场景，逐项看“职责描述与选择条件”。训练例用来帮助理解，不能代替定义。
3. 结合API的实际作用和所属对象选一项。成员名相同，不代表场景相同；例如保存优化器状态与导出模型，要按各自对象的职责区分。
4. 填写`细分场景`，用一句话说明它为什么符合该场景定义。

同模块已有候选场景也可以比较：在说明文件中查找`level=scenario`且`parent=[分类, 细分模块]`的定义记录。若模块本身也是候选，就用这些记录中的场景定义继续判断。

所有场景都不适用时，先检查所选模块是否正确。模块正确但确实缺少对应场景，才提出新场景。不能为了选到某个场景，跳到另一个模块下面直接取名字。

### 三步示例

以`Tensor.add`为例，每一步分别判断：

| 步骤 | 结果 | 简短原因 |
|---|---|---|
| 分类 | 基础计算 | 主要作用是对张量做数值运算。 |
| 细分模块 | 基础计算 | 属于普通张量计算，不是神经网络、优化器等专门模块的职责。 |
| 细分场景 | 张量类方法 | 是普通Tensor实例提供的运算方法，符合该场景定义。 |

继承成员按所属对象的用途理解。公开别名先确认实际用途，再按定义选择。不能只凭`save`、`load`、`forward`等末段名称决定三层结果。

## 没有合适定义时，怎样提出新标签

先确认上一级选对了，再检查该层现有定义和同父级候选。能够使用现有定义就沿用；只有明确缺少一种职责时，才提出新标签。

| 要新增什么 | 必须先确认什么 | 要解释什么 |
|---|---|---|
| 场景 | 分类和模块都选对了，该模块所有场景定义都不适用 | 最接近的场景为什么不适用，新场景补上什么职责 |
| 模块 | 分类选对了，该分类所有模块定义都不适用 | 最接近的模块为什么不适用，新模块负责什么工作；同时定义它下面的场景 |
| 分类 | 五个顶层分类都无法容纳这项职责 | 这是什么独立职责，为什么五类都不适用；同时定义模块和场景 |

API名称新、版本新、设备名称不同、训练例里没有该API，都不是新增标签的理由。只有一个API也可以提出新标签，关键是职责确实不同。文档不足或判断不确定时，选择最合理的完整分类，并在对应层原因中指出不确定处，不为消除不确定性新建标签。

候选名称使用简短的职责名称，不用完整API名、编号、“待审核”或泛化的“其他”代替定义。已有“其他”“工具函数”等模块也有职责范围，不能把不理解的接口都放进去。

候选定义只写到`data/run_data/<run-id>/api-classification/classification-evidence.jsonl`，通过同一回填脚本的`save_definitions`保存，调用时传入本轮`basic_information`及AI_LOOP根目录。每条定义包含：

- 层级`level`、完整父路径`parent`、名称`name`和职责`definition`。
- 适用条件`apply_when`、不适用的边界`do_not_apply_when`、例子`example_apis`。
- 现有定义为什么不适用`why_existing_does_not_fit`、审核状态`review_status=待审核`、通过后应更新的文件`reference_file`。

脚本添加`kind=definition`，并按level、parent、name更新原记录。同一个定义只保存一次，后续API可以复用，但仍属于待审核候选。`reference_file`指向对应分类的定义文件；新顶层分类暂指向本规则文件。本轮不把候选写入references，也不修改本文件的分类表。

## 结果怎样保存，审核后怎样更新

1. **填写结果。** 将三个结果分别填入数据库条目的分类、细分模块、细分场景。新增API的`分类待审核`一律为`是`，AI不能因为有把握就改为否。
2. **保存理由。** 在本轮说明文件中，按API名称保存category_reason、module_reason、scenario_reason，每层一句，最多100字。使用新标签或待审核父级时，在new_label_reasons对应层简述职责缺口，最多160字。分类结果留在数据库，不复制到每条说明中。
3. **执行写库。** 回到[Step2.1](../../steps/step2.1-api_prepare.md)，临时文件只放十一列，调用既有回填脚本。写库成功后删除临时文件；说明和候选定义留在本次运行目录，同轮可复用，不建立供下次运行复用的长期说明库。
4. **提交人类审核。** PR提供数据库分类、简短理由及候选定义。审核前不更新references。同轮已有API和定义的说明不重复追加。
5. **应用审核结论。** 审核通过后，再把新模块或新场景补入对应定义文件；新顶层分类由审核人确定定义文件，并更新本文件的分类表和链接。若名称或父级被修正，同时修正相关数据库条目和本轮记录。规则更新完成后将定义标为已审核，API的分类待审核按人类审核结论更新；未通过的候选不能加入规则。

历史规则构造和盲测结果见[分类方法说明](../../docs/how-to-classify-api-restored.md)。
