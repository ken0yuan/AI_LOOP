### 任务07：固定 PR 双端测试记录的格式和信息来源

进度：PR 填写模板、Step4.1、Step4.2 和示例已完成，本轮仅调整填写规则，复用已有执行材料。

PR 直接展示 NPU、GPU 的实际设备和真实测试结果，当 dispatcher 的 `agentname` 为 `api-adaptation` 时，使用 torch-npu 目标分支的 `.gitcode/PULL_REQUEST_TEMPLATE.md`，按 [API 适配填写模板](../templates/api-adaptation-pr-template.md)在【功能验证】栏目只保留实际测试结果表，执行端写明 NPU/GPU 及实际设备型号；已填写的样例见 [API 适配 PR 示例](../example/pr-module-call.md)。不要求额外托管证据链接，不要求测试全部通过；真实失败同样是有效验证结果。

#### 信息来源

1. NPU 使用 `results[].report`、`results[].device_validation.npu.log` 及报告关联的 JUnit。
2. GPU 使用 `results[].device_validation.cuda.report` 及该次运行已有的环境记录、JUnit、设备审计和日志。
3. 设备型号、测试汇总、报错和退出码均引用上述材料。统计保留框架原始汇总或 JUnit 原始统计，不由 AI 自填或推算；缺失项注明未记录，不填 0。

#### 展示标准

1. 分开说明执行完整性和测试结论：执行完整可以同时是测试未通过。
2. 真实断言失败保留失败项和原始报错；环境、执行异常或材料不足以形成结论时写无法判定，不直接认定 API 不支持。
3. 全部目标用例实际通过才写通过；Actions 成功、退出码为 0 或状态字段为 pass 均不能单独作为依据。
4. 实际执行环境优先于准备阶段信息，原始失败或异常不能被汇总报告中的通过结论覆盖。历史轮次保留在运行记录中，PR 不展开。
5. 在内部核对材料与待提交文件的对应关系及双端文件 SHA256，PR 不另加文件说明或哈希清单。仅整理 PR 不修改测试、不接入生成器、不重新运行测试。

涉及位置：`AI_LOOP/templates/api-adaptation-pr-template.md`、`AI_LOOP/steps/step4.2-create_pr.md` 和 `AI_LOOP/example/pr-module-call.md`。同期补齐 `templates/issue-template.md` 并对齐 Step4.1 的模板引用。不新增采集、执行或发布校验脚本，不修改 `api-adaptation` 和 `gen-torch-npu-api-ut`；自动事实核验仍归任务04。

验收重点：PR 的单张结果表能看清两端实际设备和真实测试结论；不手填统计、不隐去失败、不将缺失数字填为 0；现有材料不足时如实说明，不为填表重跑。
