# Step 2.1：API 入库、正名对齐与字段补全

本文说明[Step 2.1](../steps/step2.1-api_prepare.md)的前两步：先刷新数据库，再补全缺失的业务字段。完整字段表和命令入口见该步骤文档。

两步的分工是：第一步维护 API 名称、对外标记、存在状态和正名关系，筛出需要补全的正名；第二步只补这些正名行的缺失字段。别名行不补业务字段，已有值也不主动清空。

## 输入与字段分工

| 输入 | 用途 |
|---|---|
| 本次 `basic_information.json` | 确定本轮已准备的 Python 环境及运行目录 |
| 官方 main 文档的 `objects.inv` | 获取全量公开 API 名称和文档入口 |
| `data/api-support.sqlite3` | 读取和更新 `API支持数据` 表，`API名称`是唯一主键 |
| 本轮取得的官方 API 文档 | 补齐三级分类等信息，同一份材料直接复用 |

| 处理位置 | 负责的字段或内容 |
|---|---|
| 第一步 | 新增名称、`是否对外`、文档与 wheel 存在状态、`api首次出现版本`、`API真正名字`，以及正名变化时已有业务信息的沿用 |
| 第二步 | 正名行缺失的支持结论、等级、三级分类、`API适配分类`、适配策略、本地任务开关及分类审核标记 |

正名或独立 API 的 `API真正名字` 留空是正常状态，不属于待补缺项。该列与首次出现版本由第一步维护，不交给第二步填写。

## 第一步：刷新数据库

### 1. 获取全量文档 API

从官方 `objects.inv` 提取全部登记的公开名称及对应文档入口。索引提供名称和入口，不等于已经取得每个 API 的完整正文。

### 2. 与全库主键匹配

先按名称匹配整个数据库，不能先排除对内条目再查重。

| 匹配结果 | 处理方式 |
|---|---|
| 已有同名对外条目 | 沿用原行 |
| 已有同名对内条目 | 将`是否对外`改为`是`，沿用原行和已有业务字段，不重复插入 |
| 没有对应条目 | 新增一行 |
| 其他对内条目 | 保持原样，不参与本轮存在性核验和别名比较 |

已有对外条目的 `Tensor.*` 与 `torch.Tensor.*` 简写兼容匹配，保留原有数据库主键。

### 3. 核验全部文档 API 是否存在于 wheel

使用本轮已准备环境的解释器检查全部文档名称，包括数据库中已有的名称。确认不存在的条目标记为 `API删除，待下线`，新增名称也保留一行。

存在的条目保留已有支持结论；原为删除标记、现在重新出现的条目恢复为 `未提供`。导入或依赖异常属于核验失败，不能当作 API 不存在。

### 4. 检查文档中消失的对外 API

| 文档情况 | wheel 情况 | 数据库处理 |
|---|---|---|
| 文档中存在 | wheel 中不存在 | `API删除，待下线` |
| 文档中消失 | wheel 中仍存在 | `文档删除，待下线` |
| 文档中消失 | wheel 中也不存在 | `API删除，待下线` |

`API删除，待下线`表示入口不可用，不进入补全名单和后续适配任务。`文档删除，待下线`只记录文档缺失，不能据此判为不支持；wheel 中仍存在时，继续按适配策略和本地任务开关处理。

### 5. 比较对象身份，更新正名指向

将新增 API、内部转对外 API 与 wheel 中存在的存量对外 API 一起解析。在同一个 Python 进程中保留对象引用，以 `id()` 建立身份索引，用 `is` 确认是否属于同一对象。

每组取完整名称最短的公开 API 为正名，等长按字典序选择。

- 每个公开名称仍保留自己的数据库行。
- 正名行的 `API真正名字` 留空；其他名称直接指向正名行的 `API名称`，不形成多级跳转。
- 出现更短正名时，原正名和所有公开旧别名同步直接指向新正名。已有业务信息沿用到新正名，保留目标行已有值，只补其缺项。
- 功能相同但 `is` 为假的入口分别保留，不仅凭文档中的别名说明合并。
- `Tensor.*` 简写按完整的 `torch.Tensor.*` 名称比较长度，指向中仍使用目标行原有主键。

完成正名对齐后，检查正名行的业务字段。字段齐全的条目，包括内部转对外条目，不再进入第二步；有缺项的才需要补全。本轮的名称、状态和指向变更仍在下一项统一保存。

### 6. 保存并交接补全名单

同一事务保存新增行、对外标记、支持状态和正名指向。将本轮新入库、内部转对外或恢复上线后仍有业务字段缺项的有效正名写入 `api-refresh/new-apis.json`，按正名去重。

字段齐全的正名、wheel 中不存在的名称及其正名不进入名单。别名本身不作为待补全对象。

真正新增的行在这一步填写`是否对外=是`、`分类待审核=是`及首次出现版本；不预填三级分类和 `API适配分类`。已有条目的首次出现版本保持原值。

第一步返回 `DATABASE_REFRESHED`。补全名单非空时进入第二步，为空时跳过第二步。

## 第二步：只补正名行的缺失字段

### 1. 定位正名并复用材料

读取 `new-apis.json`，排除 wheel 中不存在的条目，通过 `API真正名字` 定位正名并去重。这里只处理最终的正名行，同一正名只补一次。

**别名行的分类、适配分类、适配策略等业务字段空着就保持空，不把正名的补全结果复制回别名。别名行已有的业务值也不主动清空。**

补全时复用本轮已取得的官方文档，缺失页面按需获取一次。三级分类、适配分类及后续用例生成共用已有材料，不各自重新提取一份。

### 2. 补齐三级分类与初步适配分类

按[API 三级分类规则](../references/api-classification/rules.md)，依次处理`分类`、`细分模块`、`细分场景`。已有层级和值保持不变，只补缺失层级。

`API适配分类`缺失时，结合前两级结果填写：

| 分类 | 细分模块 | API适配分类 |
|---|---|---|
| 基础计算 | 基础计算 | 算子类API |
| 基础计算 | 其他模块 | 框架类API |
| 其他分类 | 任意模块 | 框架类API |

只有两个层级都为`基础计算`才初分为算子类，对应用例生成的计算类；其余组合初分为框架类。该结果是后续用例生成的初始类别，后续仍要按具体 API 职责核验和细分。

已有 `API适配分类` 保留，不因本次补全而批量重写历史 Excel 导入的值。历史适配分类与三级职责分类是分别保存的信息。

### 3. 补齐其他业务字段

| 字段 | 缺失时的处理 |
|---|---|
| 是否支持 | 填`未提供` |
| API等级 | 填`L2` |
| 适配策略 | 填`补充testcase` |
| 本地是否适配 | 填`是` |
| 分类待审核 | 本轮补入分类时填`是`；其他已有审核标记保留，缺失时填`是` |

已有支持结论、等级、策略和本地任务开关保持原样。例如已有`本地是否适配=否`，不能因为进入补全流程就改成`是`。

本轮文档缓存、简短分类原因和候选定义保存到当前运行目录的 `api-classification/`，不建立供下次运行复用的长期分类说明库。

### 4. 写入结果

使用 `api-entries.jsonl` 提交待更新正名行的前十一列业务字段。已有字段照带原值，只有缺失字段填写补全结果；不在其中填写首次出现版本和正名指向。

写入脚本只更新需要补全的正名行，不更新别名行或无关条目。成功后删除临时 `api-entries.jsonl`，返回 `API_ENTRIES_READY`。

## 典型情况

| 情况 | 第一步结束时 | 第二步 |
|---|---|---|
| 真正新增、没有同对象公开入口 | 新增正名行，记录存在状态和版本 | 只补该正名行的缺项 |
| 新增名称是已有完整正名的别名 | 保留新行并指向已有正名 | 不补别名；正名齐全也不重复补 |
| 内部转对外，正名字段齐全 | 更新对外标记并完成正名对齐 | 不进入 |
| 内部转对外，正名仍有缺项 | 保留已有值，将正名交接到补全名单 | 只补缺项 |
| 新增更短名称成为正名 | 更新全组指向，沿用已有业务信息 | 新正名仍有缺项时才补 |
| API 已从 wheel 下线 | 保留行并记录 API 删除状态 | 不进入 |

`new-apis.json`是字段补全名单，不是本次适配任务名单。本次适配任务仍由问题描述决定；补全名单为空，也不表示没有需要适配的已有 API。
